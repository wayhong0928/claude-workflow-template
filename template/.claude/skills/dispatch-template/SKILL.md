# 派工 prompt 模板

> 用法：選對應模板、填空、貼進 Agent tool 的 prompt。【】是填空處。
> 通用規則：model 參數顯式指定（選型表見下一節）；每份派工 prompt 結尾都附下方「共用尾段：回報合約」，照抄不刪。

## 顯式指定 model

- 派工時一律在 Agent tool 顯式帶 `model` 參數：`haiku`／`sonnet`／`opus`。不帶時，agent 定義檔有寫 `model` 就用定義檔的（例如 `verifier` 是 sonnet），沒寫就用預設，通常是繼承主對話的模型：主對話是 opus 時浪費額度，是 haiku 時會不自覺降級。
- `/model` 選單裡出現的模型不一定包含在你的方案額度內。沒把握就只用上面三個。派了如果報模型不可用或額度不足，照 `.claude/rules/dispatch-and-verify.md` 的升降級路徑處理，不要原樣重試。
- `effort` 參數只在使用者、CLAUDE.md 或本 skill 明確要求時才帶；本 skill 沒寫要帶的派工就不帶。

**選型表：**

| 模型 | 用途 | 不要用在 |
|---|---|---|
| haiku | 規格完全明確、判斷量為零的機械工作：套已驗證的批次模式、格式轉換、逐條抄錄 | 任何需要取捨的事 |
| sonnet | 預設工作馬：搜尋、摘錄、實作、產筆記、初審；整理、抽取類的起草預設派它；read-back 類驗收（verifier 定義檔預設） | 規則互相衝突的裁決 |
| opus | 難題：跨檔重構、模糊需求、要判斷的起草、高風險判斷的第二意見、規則衝突裁決；對外主張、因果、高風險內容的語意驗收（派 verifier 時帶 `model: opus` 覆蓋） | 機械批次（浪費） |

不論派哪個模型：能用腳本抽的（固定欄位、固定格式）先寫腳本，不派模型起草。經驗上錯誤多集中在模型自己寫的句子，腳本抽取的部分很少出錯。

## 共用尾段：回報合約（每份派工 prompt 結尾必附）

```
回報規則：
- 只回：結論、關鍵證據（檔案路徑:行號）、驗收條件逐條核對結果、不確定之處。
- 長產物寫入【指定路徑或 scratchpad】，回報路徑即可，不要貼全文。
- 找不到／做不到就明說，附上你試過什麼。不准硬湊。
- 不要讀任何憑證檔（如 ~/.claude/.credentials.json）。
```

## 1. 搜尋（派 Explore，或 general-purpose；model: sonnet，簡單的用 haiku）

```
目標：找出【要找什麼：檔案／設定／某規則寫在哪／某函式定義】。
動機：【為什麼要找，找到後要拿來做什麼——讓你在多個候選之間知道挑哪個】。
範圍：從【目錄／檔案模式】開始找；已知線索：【關鍵字、可能的檔名、相關術語】。
搜尋廣度：【medium ／ very thorough（多處位置、多種命名慣例都要掃）】。
驗收條件：
- [ ] 每個結果附 檔案路徑:行號 與一句話說明為什麼是它
- [ ] 明確區分「確定就是」與「疑似」
- [ ] 找不到時列出掃過的範圍，證明不是沒找
```

## 2. 實作（general-purpose；model: sonnet）

```
目標：【做什麼，一句話】。
動機：【為什麼做、放進什麼脈絡——遇到規格沒寫到的岔路時，往這個方向偏】。
規格：
- 輸入／觸發：【】
- 預期行為：【逐條，可驗證】
- 邊界條件：【空值／中文路徑／編碼（.ps1 要 UTF-8 with BOM）等】
- 不要動的東西：【檔案／目錄清單】
完成後自驗：【怎麼跑、用什麼輸入、預期輸出長什麼樣】。
驗收條件：
- [ ] 實跑過至少一條真實路徑，回報中附執行輸出
- [ ] 未動「不要動」清單內的任何檔案
- [ ] 改動清單：每個檔案一行（路徑＋做了什麼）
```

## 3. 重構／批次修改（模式已驗證：haiku；未驗證：sonnet）

```
目標：把【模式描述】套用到【檔案清單或 glob】。
動機：【為什麼要改】。
模式（先在【1 個範例檔】上驗證過的版本）：
- 找：【舊內容的精確特徵】
- 改成：【新內容，附一個改前→改後的完整範例】
- 跳過條件：【什麼情況不要改，寧可列出來回報】
驗收條件：
- [ ] 數量核對：應改 N 個，實改幾個，跳過幾個（附跳過原因）
- [ ] 抽 3 個改過的檔 read-back，貼改動處上下文
- [ ] 除目標模式外，檔案其他內容零變動
```

## 4. 研究／取材（general-purpose；查官方文件用 claude-code-guide；model: sonnet）

```
問題：【要回答什麼，越具體越好；多個問題就編號】。
動機：【答案要用來做什麼決定】。
來源優先序：【官方文件／原始 PDF 或本機 md／網頁】；禁止用訓練記憶回答可查證的事實。
產出落檔：寫到【路徑】，主對話只要摘要。
驗收條件：
- [ ] 每個結論附來源（URL 或 檔案:頁碼／行號）
- [ ] 每題標信心：高（來源明說）／中（來源暗示）／低（推論）
- [ ] 查不到的題目明寫「查無」，不用推測填補
```

## 5. 審查／驗收（派 verifier；高風險再加一路 opus 第二意見）

model：read-back 類（檔案在不在、欄位齊不齊、引用存不存在）用定義檔預設的 sonnet；對外主張、因果、高風險內容的語意驗收帶 `model: opus`。

只用於第 2 級產出；第 0、1 級不派 verifier，分級見 `.claude/rules/dispatch-and-verify.md`「驗證不自驗」。同一段工作的多個檔案合併成一次派工。

```
待審產出：【檔案路徑清單】。
驗收條件（逐條核對）：
- [ ] 【條件一，可判定真偽的敘述】
- [ ] 【條件二】
- [ ] 檔案內引用的路徑／工具名／skill 名真實存在（抽查）
- [ ] 若產出是 hook／腳本／自動化機制（非純文件），實際觸發一次看真實行為，不能只讀設定檔判斷「應該會生效」
只報影響正確性或違反上列驗收條件的問題；全部通過就說全部通過，不要硬找意見。
背景限制：只給你驗收條件與檔案，不給原始推理過程，請獨立判斷。
回報：逐條 通過／不通過／無法判定＋證據 → 問題清單（致命／錯誤／瑕疵排序）→ 一句話總結（可收／需修）。
```

第 2 級修完一定複驗，範圍只限改過的點，另派一個 fresh-context verifier：

```
上次驗收的發現：【編號＋原文】。
怎麼修的：【每條一句＋檔案路徑:行號】。
驗收條件：
- [ ] 每條發現是否已修正
- [ ] 修改處前後有沒有引入新錯誤（只看修改處與它引用的內容，不重驗全檔）
背景限制：只給你上次的發現與修改位置，不給原始推理過程，請獨立判斷。
回報：逐條 已修／未修／新問題＋證據 → 一句話總結（可收／需修）。
```

## 單次派工前的兩問

subagent 很容易成為用量的大宗，其中多半是「把整份素材貼進 prompt」造成的冷啟動。派任何單次 subagent 前，先問自己兩句：

1. **這件事需要全套工具嗎？** 不需要就降 haiku，或改派工具較少的 agent（唯讀搜尋用 `Explore`；常用的窄工具組在 `.claude/agents/` 寫定義檔、用 `tools` 欄位列白名單，例如 `verifier`），不要預設 general-purpose。
2. **素材是要 agent 自己讀，還是我貼給它？** 能給路徑就不要把整份素材貼進派工 prompt——貼全文會讓每次派工都變成一次昂貴的冷啟動。

## 平行派工前的四項檢查

（部分依 `bojieli/ai-agent-book` 第10章彙整。）

發出多個平行派工前確認四件事：

1. **額度是否足夠。**
2. **有沒有共用寫入目標**（暫存檔或 log／路由表）——有就指定各自私有暫存路徑，或降低平行數。
3. **有沒有「通用規則 vs 明文排除特例」的邏輯陷阱**——批次操作不能無差別套用到明文排除的案例。
4. **跨檔案語義相依**——不同 agent 改的是不同檔案，但邏輯上互相依賴（例如一個重新編號、另一個引用舊編號），檔案層級沒有寫入衝突，邏輯卻互相破壞。光看「有沒有共用寫入目標」查不出這種。

派工 prompt 要明講「不要碰 session_log.md／CLAUDE.md，由主對話統一更新」，不能假設 agent 會自己避開共用檔案。

**判準**：預期 10 次以上重複操作、單一 agent 可能跑十幾分鐘以上、或多 agent 會寫到同一個檔案時，就要拆批次＋確認額度，平行上限 3。

## 多樣本評審要確保「真獨立」

（依 `bojieli/ai-agent-book` 第10章。）

派兩路各自作答再比對分歧，前提是兩路真的獨立。同一個模型、相近 prompt 跑兩次容易發生**同質趨同**——同模型在相似上下文下產生的多份意見會系統性地往同一個方向靠攏，不能自動當獨立證據（該書引用 Anthropic 實驗：30 個同時上線的 Agent 裡有 18 個各自取了同名分支）。

**多樣本評審至少要換模型**（例如一路 sonnet、一路 opus）**或明顯拉開 prompt／上下文差異**。同模型同 prompt 跑兩次不算獨立意見，只是重複抽樣。

## 續問原 agent 的禁區

已完成的 subagent 可以用 SendMessage 續問，它保有原本的 context 與快取，追問細節時比重派便宜。**唯一禁區：驗收**——要派 verifier 的驗收（第 2 級，含複驗）一律派 fresh-context 的 verifier，不得用 SendMessage 叫原 agent「再看一次」（見 `.claude/rules/dispatch-and-verify.md` 驗證不自驗一節）。

## 派工後主對話要做的三件事

1. 收到回報先對驗收條件，不要只看結論句。
2. 不過 → 走 `.claude/rules/dispatch-and-verify.md` 升降級路徑；禁止叫原 agent「再檢查一次」。
3. 有價值的教訓（新雷點、好用模式）→ 寫回 `.claude/rules/dispatch-and-verify.md`、本 skill 或專案 CLAUDE.md，同一件事只寫在一個地方。
